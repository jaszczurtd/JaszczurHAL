JaszczurHAL compile-time flags
==============================

All optional functionality is gated by `HAL_ENABLE_*` macros that follow an
OPT-IN model: by default *no* optional module is compiled in. To use a
module, define its `HAL_ENABLE_*` flag either:

- in the project's `hal_project_config.h` (auto-included via __has_include),
  e.g. `#define HAL_ENABLE_WIFI`, or
- as a compiler define, e.g. `-DHAL_ENABLE_WIFI`.

The project header is read before target auto-detection. Keep it macro-only;
derived HAL_TARGET_IS_* and HAL_BOARD_IS_* values are available only after the
raw project input has been loaded. HAL_ENABLE_* definitions used for source
selection must be unconditional `#define HAL_ENABLE_X` or
`#define HAL_ENABLE_X 1`; the only supported conditional form is a same-symbol
`#ifndef HAL_ENABLE_X` guard. Do not put feature definitions under any other
`#if`/`#ifdef`, including raw or derived target/board branches, because the
early collector reads the file textually.

Dependency propagation is automatic. Enabling a leaf module also enables every
module it depends on; you only need to list the modules you actually use.

The only opt-OUT flag is `HAL_DISABLE_ASSERTS`, kept for compatibility with
the standard NDEBUG / assert.h convention. HAL_ASSERT() is ON by default.


Target (backend) selection
---------------------------

Separate from the per-module HAL_ENABLE_* flags, JaszczurHAL selects exactly
one hardware backend via a single switch (see src/hal/core/hal_target.h). Define ONE
of the following in your `hal_project_config.h` (or via -D):

    HAL_TARGET_RP2040        RP2040 / Cortex-M0+
    HAL_TARGET_RP2350_ARM    RP2350 / Cortex-M33
    HAL_TARGET_RP2350_RISCV  RP2350 / Hazard3 RISC-V
    HAL_TARGET_STM32G474     STM32G474 (bare-metal or FreeRTOS backend)
    HAL_TARGET_MOCK          host unit-test / simulation backend

If you define none, the target is AUTO-DETECTED from the toolchain, so existing
projects need no change:

    PICO_RP2040 / RP2040 board       -> HAL_TARGET_RP2040
    PICO_RP2350 + ARM / Pico 2 board -> HAL_TARGET_RP2350_ARM
    PICO_RP2350 + RISC-V             -> HAL_TARGET_RP2350_RISCV
    STM32G474xx (CubeG4 / -D)        -> HAL_TARGET_STM32G474
    any host compiler                -> HAL_TARGET_MOCK
    bare-metal target, no match      -> compile-time #error

Selecting two targets at once is a compile-time #error. The rest of the library
uses `HAL_TARGET_IS_RP` for the RP family, exact `HAL_TARGET_IS_RP2040 /
_IS_RP2350_ARM / _IS_RP2350_RISCV` discriminators for chip-specific code,
`HAL_RP_ARCH_ARM / _RISCV` for ISA-specific code and `HAL_TARGET_NAME` for the
exact target string.

`rp_native_lib/` supports RP2040, RP2350 ARM and RP2350 RISC-V and generates
ELF/BIN/UF2 artifacts. The HAL provides `main()` and starts core 1 only when
`HAL_ENABLE_APP_TASK1` is defined. It owns USB, the optional FreeRTOS SMP
scheduler, coordinated EEPROM/LittleFS storage, and staged OTA.


Board profile selection
-----------------------

Board wiring and fitted hardware are independent from the target. Select a
profile with `JH_BOARD`; the board generator emits one selector:

    HAL_BOARD_PROFILE_RP_PICO
    HAL_BOARD_PROFILE_RP_PICO_W
    HAL_BOARD_PROFILE_RP_PICO_2
    HAL_BOARD_PROFILE_RP_PICO_2_W
    HAL_BOARD_PROFILE_RP_PICO_PIM730
    HAL_BOARD_PROFILE_RP2040_PLUS_4MB
    HAL_BOARD_PROFILE_RP2040_ZERO
    HAL_BOARD_PROFILE_RP2040_LORA_LF
    HAL_BOARD_PROFILE_RP_PICO_CORE1262_HF
    HAL_BOARD_PROFILE_STM32G474_NUCLEO_G474RE
    HAL_BOARD_PROFILE_STM32G474_NUCLEO_PIM730
    HAL_BOARD_PROFILE_STM32G474_NUCLEO_CORE1262_HF
    HAL_BOARD_PROFILE_HOST_MOCK

Pico/Pico W/PIM730 require HAL_TARGET_RP2040. Pico 2/Pico 2 W require an
RP2350 target; Pico 2 W currently requires RP2350 ARM. HAL_BOARD_HAS_USB_DEVICE,
HAL_BOARD_HAS_CYW43, HAL_BOARD_HAS_EXTERNAL_RADIO_FRONTEND,
HAL_BOARD_HAS_SX1262_RADIO, and HAL_BOARD_HAS_BLUETOOTH_CONTROLLER expose
compile-time physical facts. Profile names reported at runtime equal the board
IDs from boards/profiles, for example picow, pico2w, and pico-rm2.
The CMake registry resolves the matching Pico SDK board and validates expected
flash size. Wireless builds can control HAL_LED_BUILTIN through the pinned
JaszczurHAL CYW43 driver without enabling lwIP or the full network backend.
The Pico+PIM730 profile defaults to WL_ON=GP2, CS=GP3, combined DAT=GP4 and
CLK=GP5. HAL_CYW43_GSPI_TARGET_HZ defaults to 31250000 for both onboard and
external radios. The native transport reads the live clk_sys, computes the PIO
16.8 divider without exceeding that target and selects the matching upstream
high/low-speed sampling program. At the standard clocks this gives divider
2.0 on RP2040/125 MHz and approximately 2.402 on RP2350/150 MHz.
Changing clk_sys while CYW43 is initialized is rejected; deinitialize the
network owner, change the clock, then initialize it again.
HAL_CYW43_PIO_CLOCK_DIV_OVERRIDE_X256 remains an explicit diagnostic escape
hatch. The legacy HAL_CYW43_PIO_CLOCK_DIV_INT/FRAC8 pair maps to that override
when both values are supplied; it is no longer a board default.

The public hal_board API reports runtime states for:

    HAL_BOARD_CAP_USB_DEVICE
    HAL_BOARD_CAP_CYW43
    HAL_BOARD_CAP_EXTERNAL_RADIO_FRONTEND
    HAL_BOARD_CAP_SX1262_RADIO
    HAL_BOARD_CAP_BLUETOOTH_CONTROLLER

Use hal_board_get_info(), hal_board_get_capability_state() and
hal_board_require_capabilities(). A declared device starts inactive and moves
to available or failed when its owning driver probes/initialises it.
RP CYW43 network modules may be compiled for a board profile without radio.
Their public status APIs then return HAL_EUNSUPPORTED without hardware access.
Declared but not initialized hardware returns HAL_EUNINIT; a failed probe or
initialization returns HAL_EHW. Pico+PIM730 additionally requires the external
radio frontend capability.


Application entry flags
-----------------------

  HAL_ENABLE_APP_TASK1
    Dispatch optional app_task1() from the HAL-provided entry path. Bare RP
    launches core 1; RP FreeRTOS creates a task pinned to core 1. STM32G474
    FreeRTOS creates the second application task. Leave it undefined for
    single-loop/single-task applications.


FreeRTOS integration flag
-------------------------

  HAL_ENABLE_FREERTOS
    Opt in to native FreeRTOS availability. This does not add a public
    hal_rtos_* wrapper; applications include and use native FreeRTOS headers
    directly. Current validation/build support is staged by target:

      RP2040/RP2350:
        Uses the pinned third_party/FreeRTOS-Kernel checkout and the official
        SMP ports for RP2040, RP2350_ARM_NTZ and RP2350_RISC-V. Direct CMake
        invokes scripts/component_manager.py to prepare or verify the kernel
        automatically. The native entry creates app_task0() pinned to core 0,
        optional app_task1() pinned to core 1, and then starts the scheduler.
        The native TinyUSB pump runs as a separate task pinned to core 0.
        scripts/build_rp_native_lib.sh --freertos first invokes
        scripts/ensure_freertos_kernel.sh, which delegates to the same
        component manager. The 18_freertos_suite manifest configures this mode
        through the normal dispatcher.

      STM32G474:
        Uses the local third_party/FreeRTOS-Kernel checkout, or the path set
        with JH_FREERTOS_KERNEL_DIR. Direct CMake invokes
        scripts/component_manager.py to prepare or verify the kernel. The
        scripts/build_stm32_lib.sh helper first invokes
        scripts/ensure_freertos_kernel.sh for --freertos or an explicit
        -D HAL_ENABLE_FREERTOS; a feature found only in hal_project_config.h is
        prepared by the CMake fallback. Both paths use the same manager.
        External JH_FREERTOS_KERNEL_DIR checkouts are verified and never
        replaced. STM32 CMake builds compile an explicit kernel source list
        (tasks/queue/list/timers/event_groups/stream_buffer, ARM_CM4F port.c,
        heap_4.c), add the target FreeRTOSConfig.h include directory, and hand
        SVC/PendSV/SysTick vector ownership to the FreeRTOS port. hal_mutex_*
        uses a FreeRTOS mutex,
        hal_delay_ms() blocks with vTaskDelay() from legal task context, and
        hal_idle() yields to the scheduler from legal task context. Fallback
        delays remain available before the scheduler and from ISR/critical
        contexts. With HAL_PROVIDE_APP_ENTRY, HAL calls app_start(), creates
        app_task0() and optional app_task1() FreeRTOS tasks, then starts the
        scheduler.

        HAL-provided native entry task defaults can be overridden with:
          HAL_FREERTOS_CORE_COUNT       default 2 on native RP; allowed 1 or 2
          HAL_FREERTOS_TASK0_STACK      default 512 FreeRTOS stack words
          HAL_FREERTOS_TASK1_STACK      default 512 FreeRTOS stack words
          HAL_FREERTOS_TASK0_PRIORITY   default tskIDLE_PRIORITY + 1
          HAL_FREERTOS_TASK1_PRIORITY   default tskIDLE_PRIORITY + 1
          HAL_FREERTOS_HEAP_SIZE        RP heap_4 bytes; default 164 KiB
          HAL_USB_FREERTOS_TASK_STACK   RP USB worker; default 512 words
          HAL_USB_FREERTOS_TASK_PRIORITY
                                        RP USB worker; default
                                        tskIDLE_PRIORITY + 2

        HAL_FREERTOS_CORE_COUNT applies to native RP builds. Setting it to 1
        selects the upstream single-core scheduler path and requires
        HAL_ENABLE_APP_TASK1 to remain undefined.

        STM32G474 uses a 24 KiB heap_4 pool from its target-local
        FreeRTOSConfig.h.

        Platform stack-size overrides:
          HAL_STM32_MAIN_STACK_SIZE     bytes; overrides STM32 linker
                                        _Min_Stack_Size reserve (default 0x800)
          HAL_RP2040_STACK_SIZE         bytes; mapped to PICO_STACK_SIZE
                                        (core0 stack reservation)
          HAL_RP2040_CORE1_STACK_SIZE   bytes; mapped to
                                        PICO_CORE1_STACK_SIZE

        Full module task-safety remains conservative. Singleton/per-bus mutex
        creation uses atomic create-once fallbacks where defensive lazy creation
        is still needed; timer callback context and documented single-owner
        modules follow the FreeRTOS plan and thread-safety audit. The mock backend
        does not support HAL_ENABLE_FREERTOS. runalltests.sh enables the host
        FreeRTOS POSIX scheduler test target (JH_ENABLE_FREERTOS_POSIX_TESTS) to
        cover HAL mutex/delay and lazy create-once paths in ctest without
        hardware.


Module enable flags
-------------------

Flags use presence semantics. Supported project forms are
`#define HAL_ENABLE_X` and `#define HAL_ENABLE_X 1`. Do not use `=0`: the
production preprocessor still treats that symbol as enabled. Supported board
generation, CMake, static-library scripts, and jh-vscode reject `=0` and other
explicit values with [JH-CFG-VALUE]. Arbitrary direct compiler invocations
retain presence semantics. In definition-list inputs, every HAL_ENABLE_* entry
must be a standalone simple token separated with semicolons. Whitespace does
not separate multiple feature definitions, and CMake generator expressions are
rejected. The declarative registry lint also rejects unknown symbols and direct
requests for derived symbols.

Connectivity
  HAL_ENABLE_BLE
    Experimental BLE Peripheral with one connection, copied legacy
    advertising, bounded events, ATT MTU reporting, and static GAP/GATT
    services. Supported on RP2040 Pico W, STM32G474+PIM730, and mock. Pulls
    the pinned, non-commercial-use BTstack dependency into firmware.
  HAL_ENABLE_BLE_STREAM
    Experimental JH BLE Stream v1: one static GATT service carrying a bounded
    byte stream behind a mutually authenticated application session. Enables
    HAL_ENABLE_BLE and HAL_ENABLE_CRYPTO. A client reads the protocol version
    and capabilities without a session; payload exchange requires proof of the
    per-device secret installed with hal_ble_stream_set_secret().
  HAL_ENABLE_LORA
    Feature selection for the provider-neutral raw LoRa radio facade. Requires
    exactly one family provider: HAL_ENABLE_SX126X or HAL_ENABLE_SX127X. The public
    C/C++ declaration surface is hal/radio/hal_lora_radio.h. Opaque lifecycle
    handles support DIO-driven asynchronous TX/RX/CAD, current RSSI, provider
    capabilities, task callbacks and cancellation.
    They use a generation-tagged static pool sized by HAL_LORA_RADIO_MAX_INSTANCES
    (default 2, valid range 1..255). The facade provides raw modem presets and
    validation, blocking TX compatibility, bounded or continuous RX, packet
    metadata, CAD/calibration diagnostics, standby/sleep and time-on-air
    calculation.
  HAL_ENABLE_LORA_LINK
    Reliable private point-to-point messages over one configured hal_lora_radio
    handle. Propagates HAL_ENABLE_LORA and HAL_ENABLE_CRC. Adds 16-bit
    addressing, 32-bit message sequences, bounded ACK/retry, duplicate
    suppression and fragmentation. HAL_ENABLE_CRYPTO remains optional; when it
    is selected, the link can protect data and ACK frames with
    ChaCha20-Poly1305. The generation-tagged pool is sized by
    HAL_LORA_LINK_MAX_INSTANCES (default 2, valid range 1..255), copied TX/RX
    message buffers by HAL_LORA_LINK_MAX_MESSAGE_SIZE (default 1024, valid range
    1..4096), and peer replay windows by HAL_LORA_LINK_MAX_PEERS (default 8,
    valid range 1..32).
  HAL_ENABLE_SX126X
    Selects the pinned official Semtech SX126x provider and propagates LORA and
    SPI. The shared adapter owns validated SX1262 and experimental, software-only
    SX1261 command framing, model-specific PA/OCP limits, BUSY deadlines, RF
    switch/TCXO/regulator setup and band-aware image calibration through HAL
    SPI/GPIO. HAL_LORA_SX126X_BUSY_TIMEOUT_MS defaults to 1000 and accepts values
    from 1 through 60000 milliseconds. Conflicts with HAL_ENABLE_SX127X.
  HAL_ENABLE_SX127X
    Selects the experimental, software-only SX1276/SX1278 provider and propagates
    LORA and SPI. The HAL-owned register driver supports the common lifecycle,
    DIO IRQ mapping, TX/RX/CAD, RSSI, sleep/wake and RFO/PA_BOOST selection.
    HAL_LORA_SX127X_RESET_SETTLE_MS defaults to 10 and accepts values from 5
    through 1000 milliseconds. Conflicts with HAL_ENABLE_SX126X.
  HAL_ENABLE_WIFI
    WiFi. A profile without the selected network hardware compiles but public
    runtime access returns HAL_EUNSUPPORTED.
  HAL_ENABLE_TIME
    NTP / system time. Propagates: UDP, WIFI.
  HAL_ENABLE_MQTT
    PubSubClient wrapper. Propagates: TCP, WIFI.
  HAL_ENABLE_UDP
    Thread-safe UDP transport over the selected network backend. Propagates:
    WIFI.
  HAL_ENABLE_TCP
    TCP client/listener transport. Propagates: WIFI.
  HAL_ENABLE_HTTP_SERVER
    Small poll-driven HTTP/1.1 server over HAL TCP. Propagates: TCP, WIFI.
  HAL_ENABLE_HTTP_FILES
    File serving, ETag and upload helpers over HAL HTTP routes. Propagates:
    HTTP_SERVER, TCP, WIFI.
  HAL_ENABLE_WEBSOCKET
    Small poll-driven WebSocket server over HAL TCP. Propagates: TCP, WIFI.
  HAL_ENABLE_NET_CONSOLE
    Password-protected serial/debug mirror and command stream over HAL TCP.
    Propagates: TCP, WIFI.
  HAL_ENABLE_NET_COMMANDS
    JSON/text command dispatcher for HTTP and WebSocket control channels.
    Propagates: HTTP_SERVER, WEBSOCKET, CJSON, TCP, WIFI.
  HAL_ENABLE_BSD_SOCKETS
    Minimal POSIX/BSD socket adapter over HAL UDP/TCP. Propagates: UDP, TCP,
    WIFI. May be combined with TLS, but does not require it.
  HAL_ENABLE_TLS
    Portable BearSSL TLS client over native HAL TCP. Propagates: TCP, WIFI.
    Does not force BSD sockets; an optional BearSSL BSD transport remains
    available when both modules are enabled.
  HAL_ENABLE_HTTP_CLIENT
    Bounded one-shot HTTP/1.1 client over HAL TCP. Propagates: TCP, WIFI.
    HAL_ENABLE_TLS adds the verified HTTPS transport.
  HAL_ENABLE_OTA
    Authenticated RP update service over HAL UDP/TCP with image staging,
    trial boot, confirmation, rollback, discovery, and VS Code upload.
    Propagates: WIFI, UDP, TCP, CRYPTO, CRC.
  HAL_ENABLE_WIREGUARD
    Shared host-lwIP WireGuard wrapper. Propagates: UDP, WIFI. Requires
    host-stack L3, virtual-netif/route, stack-context and secure-entropy
    backend capabilities.
  HAL_ENABLE_CELLULAR_MODEM
    Generic AT-command engine (hal_modem_at) for cellular / serial-AT
    modems. Requires at least one backend (e.g. HAL_ENABLE_A7670),
    otherwise a compile-time #error is emitted.
  HAL_ENABLE_A7670
    SimCom A7670 LTE Cat-1 cellular modem backend.
    Propagates: CELLULAR_MODEM, UART.

    HAL_LODEPNG_ENABLE_DISK or HAL_LODEPNG_ENABLE_CPP to opt them back in.
  HAL_ENABLE_PNG_AS_BASE64
    Base64-encoded PNG helpers in tools. Propagates: CRYPTO, PNG.
  HAL_ENABLE_JPEG
    Managed TJpgDec memory-based baseline JPEG decoder with RGB565 output.
    JaszczurHAL keeps SD/LittleFS backends disabled in this utility profile.
  HAL_ENABLE_JPEG_AS_BASE64
    Base64-encoded JPEG helpers in tools. Propagates: CRYPTO, JPEG.

Test framework
  HAL_ENABLE_UNITY
    Managed Unity framework. Typically enabled only by the host-test
    CMake (root CMakeLists.txt).


Opt-out flags
-------------

  HAL_DISABLE_ASSERTS
    Compile every HAL_ASSERT() to a no-op (zero text / branch in release).
    Asserts are ON by default. Mirrors the standard NDEBUG convention.


Debug
-----

  HAL_CONFIG_VERBOSE
    Make the generated header check the complete inventory of all 93
    registered HAL_ENABLE_* and HAL_DISABLE_* symbols and emit a
    `#pragma message` for each active symbol. The report runs after the
    contextual propagation retained in hal_config.h, so it describes the
    final preprocessor state.

Rules retained outside feature registry v1
------------------------------------------

hal_config.h remains the public facade for contextual rules that registry v1
cannot express.

Conditional feature propagation
  HAL_ENABLE_EEPROM with HAL_EEPROM_TYPE == EEPROM_TYPE_AT24C256 adds
  HAL_ENABLE_I2C.
  HAL_ENABLE_GPS adds HAL_ENABLE_UART only when neither HAL_ENABLE_UART nor
  HAL_ENABLE_SWSERIAL was selected.

Provider and choice rules
  Network configuration selects exactly one backend and verifies its required
  capabilities. Provider checks cover RTC, CELLULAR_MODEM, THERMOCOUPLE, CAN,
  DIGIPOT, LORA, the GPS transport, DISPLAY and TFT.

Target and board rules
  BLE controller/target/board support; CYW43 bus, stack, profile, pin, target
  and board constraints; FreeRTOS target/toolchain/header constraints; and the
  STM32G474-only FDCAN rule remain contextual.

Defaults, tunables, layout and ranges
  These include the target-dependent EEPROM default, storage/OTA region
  layout, CYW43 pin/clock/country defaults, pool sizes, backlog and TLS limits,
  and the remaining tunable defaults and range checks.

These retained sections contain all 49 production compile-time #error checks.

Registry `resolvedFeatures` and its feature hash describe only the registry v1
closure; they do not append the two contextual propagation results. A GPS-only
request can finish preprocessing with HAL_ENABLE_UART, and AT24 EEPROM can
finish with HAL_ENABLE_I2C, even though those additions are absent from
`resolvedFeatures` and the feature hash. HAL_CONFIG_VERBOSE reports the final
preprocessor state and includes those contextual additions.
